# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

# camcore

CAM software for a LinuxCNC router/mill with an automatic tool changer and a 4th (A) rotary axis.
Modes: 2.5D, V-carve, wrapped rotary, rotary from STL, rotary wizard, indexed 3+1, desktop app, 3-axis 3D, medial-axis V-carve, adaptive pocket clearing, machine body check + vismach model, inlays (done). Guide step 12 is complete; next are the real machine's config import and first cuts once the PrintNC stands.
The full roadmap is in `docs/PLAN.md`. The step-by-step build plan is in `docs/IMPLEMENTATION_GUIDE.md`. Work one guide step per session.

## Commands
- Install: `conda env create -p .conda -f environment.yml && conda activate ./.conda && pip install -e .[dev]` (conda because OpenCAMLib, used by the 3-axis 3D ops, is only on conda-forge for current Pythons; everything else comes from pip)
- Tests: `pytest -q` (must stay green; add tests with every feature)
- Single test: `pytest -q tests/test_ops.py::test_wrap_maps_y_to_a_and_depth_to_radius`
- Inlay fit alone: `camcore inlay-fit examples/inlay_pocket_job.json examples/inlay_plug_job.json`
- Gate a job (generate + verify + LinuxCNC sim + viewer; `.ngc` written only if all pass): `camcore check examples/sign_job.json` (`--no-sim` for quick iterations, `-o DIR` output folder)
- Rotary wizard (STL in, checked job out): `camcore rotary-wizard examples/pawn.stl` (`--yes` takes all suggested answers, `--no-sim`, `--no-open`)
- Desktop app: `camcore gui examples/sign_job.json` (or `camcore-gui`; needs `pip install -e .[gui]`, included in `[dev]`)
- Generate G-code only: `camcore examples/sign_job.json -o out/sign.ngc --preview out/sign.svg` (`--post grbl` overrides the job's post)
- Dry run + 3D viewer: `camcore-verify out/sign.ngc --machine examples/machine.json --tools examples/tools.json --view out/sign_view.html`
- Rotary dry run: add `--stock examples/stock_cylinder.json`
- Tool table for the sim: `python -m camcore.tooltable examples/tools.json sim/config/tool.tbl`
- LinuxCNC sim: `cd sim && docker build -t camcore-sim . && docker run --rm -v "$PWD/../out:/work" camcore-sim check /work/sign.ngc` (exit 0 = LinuxCNC ran it all; about 1 min per example). Verified with LinuxCNC 2.9.4, see `sim/README.md`.
- Sim GUI: `docker run --rm -p 6080:6080 -v "$PWD/out:/work" camcore-sim gui /work/wrap.ngc`, then open http://localhost:6080/vnc.html. On a `camcore check` output folder it also shows the vismach machine model from `NAME_scene.json`

`out/` is gitignored scratch output. `examples/*.ngc` are committed fixtures: `tests/test_verify.py::test_examples_verify_clean` replays them. After any post or op change that alters output, regenerate `examples/sign.ngc`, `examples/sign_medial.ngc`, `examples/wrap.ngc`, `examples/pawn.ngc`, `examples/indexed.ngc`, `examples/relief.ngc`, `examples/adaptive.ngc`, `examples/inlay_pocket.ngc` and `examples/inlay_plug.ngc` from their job files and confirm they still verify clean (`tests/test_rotary_ops.py` compares the pawn, `tests/test_indexed.py` the indexed bar, `tests/test_surface3d.py` the relief, `tests/test_vcarve_medial.py` the medial sign, `tests/test_adaptive.py` the adaptive pocket and `tests/test_inlay.py` both inlay parts byte for byte).

## Architecture (keep these boundaries)
Pipeline: JSON job → `job.run_job` → list of `Toolpath` (IR) → `post.get_post(name).emit(paths)` → G-code → `verify.run` (independent replay) → LinuxCNC sim. `camcore/check.py` (`camcore check`, dispatched from `cli.py`) runs the whole chain and is the only path that should produce programs for the machine.

- `camcore/job.py`: builds named shapes (rect/circle/polygon/svg/dxf/union/difference/mirror), merges `defaults` into each operation, and dispatches by name with `getattr(ops, spec["op"])(shape, tool, **params)`. A new op must be exported from `ops/__init__.py`, and its keyword args are the job-file keys. Special cases live here: `drill` takes `points` instead of a shape; a `vcarve` with `clear_tool` adds a pocket pass first, and so does an `inlay` (always). An op with `"index"` (or the job's `"index"`) is built once in face coordinates and placed on each A angle by `index_nodes` / `ops.index` (retract above `stock_reach` + `index_clearance`, rapid A alone, Z raised by the face top); its passes become nodes `id@A<angle>` with a 4th entry, the angle. `rotary` wrapping is applied to every path that is neither indexed nor a model op after all ops are built, and the optional `"tool_order": "minimize_changes"` regroup runs last (stays on the tool, then on the face).
- `camcore/ops/*`: geometry + tool + params in, `Toolpath` IR out. Ops never write G-code.
- `camcore/toolpath.py`: the IR (rapid/feed moves with X Y Z A; `None` means the axis is unchanged). Every mode emits it; posts, viewer and checks consume it.
- `camcore/post/*`: IR to G-code per controller, registered in `post/__init__.py` `POSTS`; `job_post(job)` applies the job's `"post_options"`. The LinuxCNC post fits G2/G3 arcs to feed runs with `camcore/arcfit.py` (tolerance against the original segments, not just the vertices); ops still emit only lines. `linuxcnc.py` is the primary target (T/M6 + G43, next-tool staging, G93 for A moves, G64 P blending). `LinuxCncPost.indexed(tp)` (A only in rapids that move nothing else) keeps a path in G94 with arcs and always writes its A. In G93 paths every axis is written the first time it appears (the position after a tool change is unknown), and a feed before X, Z and A are known is refused. After every M6 the post moves to the path's first X Y (Y0 for wrapped paths) and A at the G53 Z0 height before any Z move (`_position`); verify refuses a Z move down before X and Y are set. `grbl.py` is secondary (M0 pause on tool change, refuses A moves).
- `ops/vcarve.py` `method="medial"` + `ops/medial.py`: scipy Voronoi of the boundary sampled every 4 x `tolerance`; ridges inside, not between neighbouring samples, kept where dropping them would leave more than `tolerance` at the wall (r / cos(phi/2) - r); a shape with no ridge left (a round dot) is one plunge at its deepest point. Chain points carry exact clearances (`Clearance`, distance to the boundary segments), and decimation keeps every segment no deeper than the clearance anywhere along it (no gouge) and leaves at most `tolerance`. Above the cap (bit size or `max_depth`) the axis is cut off and the inset contour at the cap is cut first. A sharp peak (a triangle's incentre) cannot be reached by any path gentler than the V walls without gouging, so medial needs `entry="plunge"`; chains start at corner tips where they can and link through already-cut nodes. `tests/test_vcarve_medial.py::groove_error` measures the cut on verify's heightmap against the ideal groove: keep it passing.
- `ops/pocket.py` `method="adaptive"` + `ops/adaptive.py`: `stepover_ratio` is the width of cut kept everywhere. A grid model of the material left (cells about D/50, tool discs at sub-cell shifts) steers every R/6 step to the direction whose cut is `width` wide (bisected), climb side towards the material; a pass ends in air or above `OVERLOAD` x width, the next starts at the nearest cell just beside the material (link at depth through cleared air, else jump). Each part is bored by a helix at its widest point (`polylabel`), again behind a neck the passes cannot get through; parts too narrow for a helix fall back to offset loops with a note. The XY plan is made once and replayed per Z level, each followed by a ramped wall pass. `tests/test_adaptive.py::cut_widths` measures the cut width independently on a fine grid: keep it passing.
- Inlays: `ops/inlay.py` (`"op": "inlay"`, one job per part; `job._inlay` adds the clear pass from `inlay_clear_area`). Pocket = flat-bottom vcarve to `pocket_depth`; plug = the design mirrored about its bbox centre line (`shapes.mirror`), a vcarve of a band around it with `start_depth` s = pocket_depth - glue_gap capped at s + surface_gap (only the walls are kept, `keep`), flange cleared flat to the frame edge (the whole box stock grown by the clear tool radius, or `plug_margin`), plus plunges and runs at depth s into notches sharper than `SHARP_NOTCH` (the medial axis stops short of a tangent cusp; any tip outside the design at depth s is gouge-free). `camcore/inlay_fit.py` (`camcore inlay-fit`, and `check` when the plug op has `"fit_with"`) replays both programs with verify at `FIT_RES` as G1 (verify's arc chords lie res/4 inside, 0.09 mm on a 60 deg wall), moves the plug grid so each pocket cell lands on a plug cell (no interpolation: thin notches read wrong), flips the plug and drops it to first contact; it fails on bottom/flange gaps more than 0.1 mm off or a median wall gap above 0.1 mm (a steeper plug bit seats on the rim at the right height with gaping walls).
- Reliefs (in progress, `docs/relief_plan.md`, ported from Reliefwerk; phases 1-3 of 7 done): `camcore/relief/` is a design front end like `wizard.py`: it writes ordinary jobs plus geometry and never toolpaths or G-code. `relief/heightfield.py`: raw fields are 0..1 arrays (1 = high, row 0 = back edge) from an image (Pillow; 16-bit over 65535, transparent = low) or an STL (`stl.py` mesh, `view_triangles` z/y/x, `drop`: exact barycentric height of the highest non-vertical triangle at each grid point). `prepare` turns clockwise, mirrors, crops (`cover`) or stretches to W x H mm, blurs with sigma in mm per axis, then black/white point (percent), gamma, invert. `HeightField.sample(x, y)` is bilinear in mm, Y up, grid on the corners (cell = W / (nx - 1)). `relief/relief3d.py`: the field as a closed STL block (top Z = -depth (1 - h), optional frame at Z0 with its edge nodes doubled so the wall is vertical, sides down to the stock bottom) plus an ordinary job: box stock, `surface_rough` (floor = -depth + stock_to_leave) and `surface_finish` rasters (boundary = the frame edge grown by the ball radius). `check_design` refuses what Reliefwerk allowed: finishing alone deeper than the ball's step down, a rough tool with flutes shorter than the depth, less than `MIN_FLOOR` under the relief. Example: `python examples/relief/make_example.py` writes `examples/relief/` (waves.png, waves3d_job.json, waves3d.stl); `tests/test_relief_3d.py` regenerates it byte for byte. `relief/lamella.py`: strips `thickness` thick with `gap`, centred across the artwork (`layout`), labels V01.. (front to back strips, left to right) / H01.. (rows, back first); profile = base + relief x h sampled every `step`, averaged over `SAMPLES_ACROSS` lines across the thickness; outline in part coordinates (X along, bottom edge on Y0), no tool offset, simplified within `tolerance`. `cut_outline` = the part as the cutter leaves it (closing by the cutter disc), for nesting and plans.
- Machine body: `camcore/body.py` (plain geometry, no ops/posts) reads the machine JSON's `"body"`: spindle parts relative to the nose (tip + the tool's `"gauge_length"`), the gantry (moves with Y), fixed obstacles, and the rotary unit (only for rotary stock; it sets a rotary job's G54 from the stock's `"chuck_hold"`, `Machine.offset_for`, which `check` also uses for the sim). Parts are axis-aligned boxes and cylinders along Z or X with exact pair tests (`overlaps`). verify sweeps them along every move (`BODY_STEP`) against the obstacles and the cut stock; `wizard.reach` uses `jaw_reach` so suggested stock lengths keep the spindle off the chuck. `check` writes `NAME_scene.json` (`body.scene` plus the INI, G54 and tool table) that `sim/camcore_vismach.py` draws next to AXIS. `tests/test_body.py` pins the geometry and messages.
- `camcore/ops/rotary.py`: wrap = Y becomes A (deg = Y / r), Z0 is on the rotary centreline, so cutting Z = radius + depth.
- `camcore/verify.py`: independent G-code replay with machine + stock model (heightmap for box stock, exact flat/ball/bull/V profiles at its cells; for rotary stock, cylinder or `bar`, a radius map over (X, A) whose cells are rays from the axis, cut by the exact tool body with `Stock._ray_interval` at any tool Y; the viewer's `rayInterval` is a JS port, kept identical: `tests/test_indexed.py` compares them through node). It parses G-code text (G0/G1, and G2/G3 replayed as chords through the same checks) and must never import ops or posts, so it stays an independent check of their output. `verify_cli.py` is its CLI.
- Import: `svg.py` (own parser, affine transforms applied before flattening), `dxf.py` (ezdxf `make_path` + `flattening`), both via `shapes.py` (`join_chains`, even-odd `rings_to_geom`). Open/unsupported geometry is an error, never silently dropped.
- Rotary from STL: `stl.py` loads and places the mesh (model frame = machine frame at A = 0, rotary axis = model X; `revolve` builds solids of revolution). `cylmap.py`: `radial_map` ray-casts r(x, A) (own vectorised Moller-Trumbore, no rtree/embree), `tool_map` dilates it per cutter in closed form, treating everything between the axis and r along each ray as material (conservative). The tool looks along u(A) = (0, -sin A, cos A), matching the viewer and verify's cylinder stock (ISO sign: +A turns the part by -A); `tests/test_cylmap.py` pins this.
- `ops/rotary3d.py`: `rotary_rough` / `rotary_finish`, dispatched by `job.py` for ops with `"model"` (stock diameter from the cylinder stock). Paths interpolate `_envelope` (3x3 max of the no-gouge grid), which is provably above the sampled model between nodes; plain interpolation gouged 0.17 mm at a ball's edge contact. `decimate` compares dropped points with the move at the same X/A position (the controller moves X, A, Z together), with A relative to the move start; nearest-point distance hid 0.13 mm Z errors on steep flanks. `tests/test_rotary_ops.py::worst_gouge` checks paths against the model by brute force: keep it passing. Rotary-op paths are not wrapped, and `job.continue_a` shifts each by whole turns to start near the previous A.
- 3-axis 3D: `camcore/surface.py` wraps OpenCAMLib (drop-cutter via `BatchDropCutter`, `Waterline`), imported lazily. It moves the mesh near the origin and leaves out triangles with no XY area: OpenCAMLib's inside-facet test is in XY and divides by zero on vertical facets (contours grew 12 mm spikes); leaving them out is exact for closed meshes (a cutter touching a vertical facet also touches the edge above). Every waterline point is checked with the drop-cutter (`_check_loop`: the cutter grown by `CHECK_TOL` must not reach the level there and shrunk by it must, so it is at most 0.01 mm off touching, in 3D; `cutter`/`drop_points` take a negative leave for the inner offset) and a bad contour raises. Probing across the contour instead refused correct hairpin tips (a valley the cutter just fits into). OpenCAMLib keeps raw pointers: hold the STLSurf and cutter in Python variables for the whole run (a temporary segfaults). Waterline loops are canonicalised (start point, order) because its threads start them anywhere; examples must regenerate byte for byte. `ops/surface3d.py`: `surface_rough` (per level: boundary minus waterline of the cutter grown by the leave, cleared by `pocket.clear_levels`), `surface_finish` raster (one zigzag polyline dropped with midpoint refinement in both directions: beside a wall the needed height is a step) and waterline (fiber spacing bounded so chords stay within tolerance). Decimation there is one-sided (never under a computed point, never on the wall side of a contour). `job.py` dispatches `SURFACE_OPS` (box stock, no A, not wrapped or indexed). `tests/test_surface3d.py::worst_depth` checks paths against dense model samples by depth inside the cutter body (not vertically: on steep walls that overstates): keep it passing.
- Ops report adaptations (fewer tabs, no lead, ...) in `Toolpath.notes`; `camcore check` puts them in the report.
- `camcore/wizard.py` (`camcore rotary-wizard`): questions only; it writes an ordinary job (`build_job`) and hands it to `check.check`, never G-code itself. Questions go through `Asker` (flag value, else `--yes` default, else prompt until valid), so tests drive it with a scripted `input_fn`. It owns the chuck layout (`layout`: stock long enough that tools stay `JAW_CLEARANCE` off the jaws) and the machine's `a_max_diameter` limit.
- `camcore/project.py` (no Qt) + `camcore/gui/` (PySide6, `camcore gui`): the desktop app edits an ordinary job dict and never makes toolpaths. Parameter forms come from the op signatures (`project.op_params`), inherited values from `job.param_sources`/`job.cutting_data` (the code `run_job` merges with), Save As rebases relative file paths (`project.rebase`). Preview and Export save the job and run `check.check` in a thread (`gui/runner.py`): Preview without the sim into a scratch folder, Export with the sim into the output folder. The wizard dialog builds its form from `wizard.QUESTIONS` (the CLI's questions, defaults and validators, driven by a `Session`), so the two cannot drift. GUI tests (`tests/test_gui.py`, pytest-qt) run offscreen with `--disable-gpu` (WebGL under the offscreen platform crashes Chromium); `CAMCORE_GUI_NO_WEBENGINE=1` replaces the embedded viewer with an Open-in-browser button.
- `camcore/viewer.py` + `viewer_template.html`: self-contained HTML player (vendored three.js r128 in `camcore/vendor/`, shipped as package data).
- `sim/`: Docker image with Debian trixie's `linuxcnc-uspace` (2.9.4, non-setuid `rtapi_app`), XYZA sim config in `sim/config/`, headless `run_check.py`. `entrypoint.sh` picks up `/work/tool.tbl`, `/work/machine.ini` and `/work/machine.var` (G54) if they are mounted.

- `machine/`: provisional profile of the target machine (PrintNC V4 Metalcutter, still being built): verify JSON plus a matching sim INI and G54 `.var`. Keep the three in sync; `examples/machine.json` stays the small fixture the tests use. See `machine/README.md`.

## Conventions
- Units: mm and degrees everywhere internally.
- Climb = wall on the right of travel (M3 spindle): `rings(..., wall_outside=True)` for pockets, inside profiles and V-carve.
- Offsets and circles go through `ops/common.offset()` / `quad_segs()` so chords stay within 0.005 mm of the true arc; coarser geometry won't be refit to arcs.
- Machine conventions: rotary A turns around X; Z0 on the rotary centreline for rotary jobs; Z0 at the stock top for flat jobs.
- Tools come from `examples/tools.json`-style libraries; `number` is the ATC pocket and the LinuxCNC tool number. Per-material feeds live under a tool's `"cutting"` (stripped by `Tool.from_dict`, merged in `job.run_job` by op signature). Ordering is `job.order_paths` (dependencies via `"id"`/`"after"`).
- ATC (PrintNC: Benchworks, 6 pockets, M6 remap measures length): camcore emits only `Tn M6` + `G43 Hn`. verify enforces `atc_pockets`, `probe_tool` (never with spindle on) and the real `tool_table` from the machine JSON. `center_cutting` (default false) gates every straight plunge.
- Ops never plunge into material unless `entry="plunge"` and the tool is centre-cutting: entries live in `camcore/ops/entry.py` (ramp along the contour, helix for pockets). Tabs: `count`/`spacing` (evenly along each contour) or `at` (points on the part edge, `profile.place_tabs` projects each onto its nearest contour; relief lamellas put them on the glued bottom edge). Profiles are built in `camcore/ops/contour.py`: distance-along-contour parametrisation where depth = max(base ramp/level, tab profile), emitted exactly at kinks and crossings (no sampling). verify enforces the same rule independently.
- Every new op needs: a unit test on geometry (depths, offsets), a run through `camcore.verify.run` with zero errors, and an example job.
- Never weaken a verify check to make a test pass. If a check is wrong, fix the check and add a test that shows why.
- Generated G-code must pass `camcore check` (with the sim) before it is called done.
- Jobs must carry a `"stock"`; `camcore check` refuses jobs without one.

## Safety
This software drives a real machine. Any change to posts, rotary math or verify needs a test that pins the exact G-code or numbers it produces.
